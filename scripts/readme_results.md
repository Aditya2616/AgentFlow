Everything in this section is generated by `scripts/check_numbers.py` from the result files in `evals/results/`, and a fast
test fails if the README disagrees with them. All numbers below are Qwen3-0.6B on a GPU in {{dtype}} (device: {{device}}; the GPU
was only a speed choice and the code runs the same on a CPU), the {{n_tasks}}-task suite, greedy decoding. Model replies are
cached by prompt, so the three arms share replies wherever their prompts match, which makes **model calls** the fair cost
measure here, not wall-clock seconds. Reproduce with `agentflow ablate --rates 0,0.15,0.3,0.5 --seeds 5` followed by
`agentflow eval-report`. Files: `evals/results/dose/*.json` (one per cell), `DOSE.md` (full tables with the paired tests),
`FAILURES.md`, `SUMMARY.md`.

**Three arms.** *No verifier*: every result is passed on unchecked. *Retry only*: a tool call that raises is retried
with the error text (the same limit of {{max_attempts}} tries), but nothing else is checked and there is no re-plan; when the
retries run out the run fails. *Full verifier*: result checks, retries and re-plans, plus the email send guard.

**Two kinds of injected fault.** *Transient*: the tool call raises a timeout. *Silent*: the tool succeeds but returns a
well-formed wrong result (no search hits, zero SQL rows, empty Python output, or a document cut to 40 characters).
Rates are per tool call, and each (task, seed) pair has its own seeded fault stream. Rate 0 is one run per arm (greedy
decoding makes the seeds identical); the other rates are {{n_tasks}} tasks x {{seeds}} seeds = {{runs_per_cell}} runs per arm.

What the numbers say, with the caveats that matter:

* **Clean tasks: the verifier does not help.** The three arms pass {{clean_off_k}}, {{clean_retry_k}} and {{clean_full_k}} of
  {{n_tasks}} ({{clean_off_pct}}, {{clean_retry_pct}}, {{clean_full_pct}}), and {{fail_all}} tasks fail in every arm.
* **Transient failures are mostly a retry story.** Retry only holds up to 30% ({{transient_30_retry}} against
  {{transient_30_full}} for the full verifier, paired exact p = {{transient_30_p_full_retry}}) while no verifier falls to
  {{transient_30_off}}. Only at 50% does the full verifier pull ahead of retry only ({{transient_50_full}} against
  {{transient_50_retry}}, p = {{transient_50_p_full_retry}}), because it can re-plan once the retries are used up.
* **Silent wrong results are where checking matters.** Retry only is not distinguishable from no verifier at 50%
  ({{silent_50_retry}} against {{silent_50_off}}, p = {{silent_50_p_retry_off}}), because nothing raised and its retries
  never fire. The full verifier is ahead of retry only by {{silent_gap_30}} points at 30% ({{silent_30_full}} against
  {{silent_30_retry}}, p = {{silent_30_p_full_retry}}) and by {{silent_gap_50}} points at 50% ({{silent_50_full}} against
  {{silent_50_retry}}, p = {{silent_50_p_full_retry}}); at 15% the gap is not significant (p = {{silent_15_p_full_retry}}).
* **It costs model calls.** At 50% silent faults the full verifier uses {{silent_50_full_calls}} model calls per task
  against {{silent_50_retry_calls}} for retry only.
* **Not everything is caught.** A cut-off document is a well-formed, non-empty result and the verifier has no check for
  it. The silent faults it recovers are the empty ones.
* The p-values are paired sign tests over (task, seed) pairs. Seeds of one task are not independent, so they are
  optimistic. The {{n_tasks}} tasks are my own and few.

### The pointless email (t23) and the send guard

In the first run the model sent an email to an invented address on a task that asked for none. The send guard is a check on
side-effecting steps: an email step is dropped from the plan when the request names no recipient, and an email whose
address the request does not name is rejected before anything is written. Measured on the clean run:

{{extra}}

Without the guard the model wrote {{mail_noguard}} emails, {{mail_unasked_n}} of them on tasks that named no recipient
({{mail_unasked_ids}}). With it, {{mail_guard}} emails were written, and {{mail_guard_unasked}} of those were on a task
without an address ({{n_addr_tasks}} suite tasks name one). The guard run passes {{guard_k}} tasks against {{noguard_k}}
without it; the one task that changed from pass to fail (t23) is the checker's phrase list described above, not an email. The
guard is a rule about the request text, not a judgement: it would block a legitimate send to an address the user did not type.

### Larger model

Qwen2.5-1.5B-Instruct (about 3 GB in float16) was run on the clean suite only, before the send guard existed, so it is
not comparable with the Qwen3-0.6B rows in every detail. It passed {{big_off_k}} of {{n_tasks}} without the verifier and
{{big_on_k}} of {{n_tasks}} with it: bigger did not mean better here. Its first, uncached pass took {{big_seconds}} seconds per
